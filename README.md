## What Is LiteLLM?

LiteLLM is a **proxy that sits between your applications and your LLM backends**
(Ollama, vLLM, OpenAI, etc.). Instead of your tools pointing directly at a model server,
everything goes through LiteLLM first.

```
Your App (Pulse / Canvas / Charisma)
        │
        ▼
  ┌─────────────┐
  │   LiteLLM   │  ← The proxy (port 4000)
  │   Proxy     │     - Checks your API key
  └──────┬──────┘     - Applies rate limits
         │             - Logs token usage
   ┌─────┴──────┐      - Routes to best backend
   ▼     ▼     ▼
Ollama  vLLM  Whisper
 SA-1   SA-1  Server
 SA-2         (UK)
```

**Without LiteLLM:** Tools point directly to Ollama. No visibility, no key control,
no billing evidence. Anyone inside the network can use the GPU for free.

**With LiteLLM:** Every request has a team key. You see exactly who sent it,
what model they used, how many tokens, and what it cost.

## Understanding the Key Concepts

### How Routing Works

LiteLLM uses the **model_name** in your config to group backends.
When two entries share the same `model_name`, LiteLLM treats them as a pool
and applies your chosen `routing_strategy`.

```yaml
# Both entries share model_name: gemma
# LiteLLM automatically load balances between them
- model_name: gemma
  litellm_params:
    api_base: http://ollama-sa-1:11434    ← Server 1
    rpm: 60

- model_name: gemma
  litellm_params:
    api_base: http://ollama-sa-2:11434    ← Server 2 (same model_name!)
    rpm: 60
```

Routing strategies:
- `least-busy` — routes to the backend handling the fewest active requests
- `latency-based-routing` — routes to the fastest-responding backend
- `usage-based-routing` — routes to backend with most remaining RPM capacity
- `simple-shuffle` — random selection (simplest, good for identical backends)

---

### How Failover Works

```yaml
router_settings:
  fallbacks:
    - gemma: ["fallback-model"]   ← If all 'gemma' backends fail, use this
  num_retries: 3                  ← Retry 3 times before giving up
```

Flow:
1. Request comes in for `gemma`
2. LiteLLM tries ollama-sa-1 → fails (server down)
3. LiteLLM tries ollama-sa-2 → fails (also down)
4. LiteLLM tries vllm-sa-1 → fails
5. LiteLLM switches to `fallback-model` automatically
6. Application gets a valid response — no error seen by the user

---

### How Rate Limiting Works

```yaml
- model_name: gemma
  litellm_params:
    rpm: 60       ← Max 60 requests per minute on this backend
    tpm: 100000   ← Max 100,000 tokens per minute on this backend
```

When a key hits its limit, LiteLLM returns:
```
HTTP 429 Too Many Requests
retry-after: 60
```

Your application code should handle this:
```python
if response.status_code == 429:
    retry_after = int(response.headers.get("retry-after", 60))
    time.sleep(retry_after)
    # retry the request
```

---

### How Team Billing Works

Each team has:
- A dedicated API key
- A monthly spend budget (e.g. $50)
- RPM/TPM limits
- An allowed model list

LiteLLM tracks `tokens_in` and `tokens_out` per request.
When you've bound costs to models (via `set_model_costs.py`), it converts
those tokens into USD automatically.

Monthly billing report = query the `/global/spend` endpoint or read Grafana.

### How Whisper Transcription is Routed

The problem your supervisor described:
> "Whisper downloads a PyTorch model and loads it on local hardware.
> I can't evidence how much of the shared infrastructure it's using."

The solution:
1. Run **faster-whisper-server** — it serves Whisper as an OpenAI-compatible
   `/audio/transcriptions` endpoint (like Ollama does for chat models)
2. Register that endpoint in LiteLLM as a model
3. Your worker code sends audio to LiteLLM, NOT to Whisper directly

```python
# BEFORE (no visibility):
import whisper
model = whisper.load_model("distil-v3")     # Loads weights on local GPU
result = model.transcribe("call.wav")        # No usage tracking possible

# AFTER (full visibility via LiteLLM):
import openai
client = openai.OpenAI(
    api_key="sk-uk-transcription-...",
    base_url="http://localhost:4000",         # LiteLLM proxy
)
with open("call.wav", "rb") as f:
    result = client.audio.transcriptions.create(
        model="whisper-transcription-uk",     # LiteLLM routes to faster-whisper-server
        file=f,
    )
# LiteLLM now tracks: which key, which model, how many tokens, what it cost
```

To run faster-whisper-server:
```bash
docker run -d \
  --gpus all \
  -p 8000:8000 \
  fedirz/faster-whisper-server:latest-cuda \
  --model distil-whisper-large-v3
```

## Useful LiteLLM API Calls

All requests require `Authorization: Bearer <your-master-key>`.

```bash
# Health check
curl http://localhost:4000/health

# List all models
curl http://localhost:4000/models \
  -H "Authorization: Bearer $LITELLM_MASTER_KEY"

# List all teams
curl http://localhost:4000/team/list \
  -H "Authorization: Bearer $LITELLM_MASTER_KEY"

# View global spend
curl http://localhost:4000/global/spend \
  -H "Authorization: Bearer $LITELLM_MASTER_KEY"

# Send a chat request (using Pulse team key)
curl http://localhost:4000/chat/completions \
  -H "Authorization: Bearer sk-pulse-your-key" \
  -H "Content-Type: application/json" \
  -d '{"model": "gemma", "messages": [{"role": "user", "content": "Hello"}]}'

# View key info
curl "http://localhost:4000/key/info?key=sk-pulse-your-key" \
  -H "Authorization: Bearer $LITELLM_MASTER_KEY"
```

## Common Issues

| Problem | Likely Cause | Fix |
|---|---|---|
| LiteLLM won't start | `.env` has `CHANGE_ME` values | Fill in all credentials in `.env` |
| `connection refused` on port 4000 | Docker not running | Start Docker Desktop |
| Model returns 404 | Backend server not reachable | Update `api_base` in config to your server IP |
| 403 Forbidden | API key doesn't have model access | Check team's `models` list in `setup_teams.py` |
| 429 Too Many Requests | Hit RPM/TPM limit | Increase limits in config or add more backends |
| Postgres unhealthy | Wrong password | Check `POSTGRES_PASSWORD` matches in `.env` |
